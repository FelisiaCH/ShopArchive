# เปลี่ยน TOFU เป็น QR pairing ก่อนล็อก BCN

BCN draft ล็อกได้ แต่ต้องแก้ก่อนเขียนโค้ด เพราะ**มีสาม decision ที่ทำไม่ได้ตามที่เขียน** และ login placeholder มีช่องโหว่ตั้งแต่การเชื่อมต่อครั้งแรก: iOS client ใน P11 ซึ่งมี Info.plist แค่ `NSLocalNetworkUsageDescription` + `NSBonjourServices` จะต่อ server self-signed ไม่ติดเลย เพราะ Apple ห้ามคลาย trust ขณะ ATS เปิดและบล็อกการต่อ IP ตรงตั้งแต่ iOS 17, Configurate YAML ที่ release แล้วเก็บ comment ไม่ได้ (P03), `System.setProperty` ย้าย `java.io.tmpdir` หลัง JVM start ไม่ได้ (P02) และ setup code 48 ชั่วโมงที่ส่งผ่านช่อง TOFU ถูกคนกลางบน Wi-Fi สาขา relay ไปยึด account ได้ ข้อเสนอให้ lock คือ **login แบบ device pairing** ที่ console หรือ admin ออก QR พก SPKI pin กับ code ใช้ครั้งเดียว ≥112 bit อายุ ≤10 นาทีเป็นทางเดียวที่อุปกรณ์ใหม่เข้าระบบได้ ใช้ opaque token ต่อคู่ (device, user) มี PIN รายคนที่ server ตรวจ ยืนยัน password ซ้ำทุก 30 วัน และใช้ backoff แทน hard lockout ส่วน **iOS** ใช้ AltStore Classic 2.3 ได้กับ iPhone ไม่กี่เครื่อง โดย floor จริงคือ iOS 17.4 ต้องมี Apple ID ของร้านเครื่องละตัวและ AltServer เปิดตลอดทุกสาขา แล้วย้ายไป Apple Developer Program $99/ปี (TestFlight internal หรือ ad hoc) ทันทีที่มีสาขาไม่มีเครื่อง AltServer ด้าน **remote access** ต้องตั้งต้นว่าร้านอยู่หลัง CGNAT เพราะลาวมี IPv4 ราว 116k address สำหรับผู้ใช้เน็ตราว 5 ล้านคนและใช้ IPv6 ไม่ถึง 1% ลำดับที่เสนอคือ public IPv4 + port forward พอร์ตเดียวซึ่งไม่พึ่งใครเลย ถ้าไม่ได้ก็ใช้ relay แบบ TCP passthrough บน VPS ที่เจ้าของคุมเองโดย TLS และ pin วิ่ง end-to-end หรือยอมเป็น LAN-only + outbox เพราะหลัง CGNAT ไม่มีทางไหนที่ไม่ต้องมีเครื่องใดเครื่องหนึ่งอยู่บน internet กับดักที่ plan ยังไม่เห็นคือเมื่อเปิด relay ทุก request จาก internet จะเข้ามาเป็น loopback หรือ RFC1918 ซึ่ง MASTER นับเป็น LAN ทำให้ web client หลุดออก internet และ per-IP throttling เห็นทุกคนเป็นคนเดียว

## Login ต้องเริ่มจาก QR pairing ไม่ใช่ password

ทิศทางหลักของ placeholder ถูกแล้วและควรคงไว้ การสร้าง owner จาก console (P06 ให้ first run แนะนำ `user add` แล้ว `op`) เป็น pattern ที่ self-hosted app ซึ่งไม่มี email ใช้กันทั้งหมด Home Assistant เขียนไว้ว่า **"There is no way to recover the owner credentials"** จากใน UI และให้กู้ผ่าน console ด้วย `auth reset --interactive` ([HA: Locked out](https://www.home-assistant.io/docs/locked_out/)) Immich มี `immich-admin reset-admin-password` ([Immich server commands](https://docs.immich.app/administration/server-commands/)) และ Nextcloud มี `occ user:resetpassword` ([Nextcloud occ](https://docs.nextcloud.com/server/stable/admin_manual/occ_users.html)) ระบบที่ให้ "คนแรกที่สมัครผ่าน web ได้เป็น owner" ต้องอุดช่อง race เอง เช่น Portainer หยุด service ถ้าไม่มีใครสร้าง admin ภายใน 5 นาที ([Portainer](https://docs.portainer.io/faqs/installing/your-portainer-instance-has-timed-out-for-security-purposes-error-fix)) BCN ไม่มีช่องนี้ตราบใดที่**ไม่เพิ่ม web onboarding** สิ่งที่ต้องรื้อคือสามจุดที่ placeholder ผูก trust ไว้กับตำแหน่งในเครือข่าย ได้แก่การเชื่อมต่อครั้งแรก session ที่ไม่มีเพดาน และ lockout ที่อิง IP

### Setup code 48 ชั่วโมงบนช่อง TOFU เปิดทางให้ MITM relay

ลำดับใน P07/P11 ตอนนี้คือ staff พิมพ์ address แล้ว client ต่อครั้งแรกแบบ TOFU และ pin SPKI จากนั้นจึงส่ง setup code ถ้าผู้โจมตีอยู่บน Wi-Fi สาขา ตั้ง rogue AP หรือปลอม DNS ได้ มันจะยื่น cert ของตัวเอง client จะ pin cert นั้น และ code จะถูกส่งถึงผู้โจมตีซึ่ง relay ต่อไปยัง server จริงและได้ account ไปทั้งก้อน เพราะ pin ปกป้องเฉพาะการเชื่อมต่อ*หลัง*ครั้งแรก mDNS ช่วยไม่ได้ แม้ Syncthing ที่ใช้ pinning แบบเดียวกันก็เตือนว่าบน local discovery **"any device can in theory announce itself for any device ID"** ([Syncthing: Device IDs](https://docs.syncthing.net/dev/device-ids.html)) P11 มีขั้นให้ผู้ใช้ยืนยัน fingerprint อยู่แล้ว แต่ Chromium เองให้เหตุผลตอนบล็อก WebAuthn บนหน้า cert error ว่าผู้ใช้ "may skip the interstitial" ([Chromium, 2022](https://lists.w3.org/Archives/Public/public-webauthn/2022Nov/0135.html)) การหวังให้ staff เทียบ hex เองจึงไม่ใช่ control ที่พึ่งได้

ทางแก้คือให้การเชื่อมต่อครั้งแรก**ถูก verify ด้วยสิ่งที่อยู่นอก TLS** NIST SP 800-63B-4 (final ก.ค. 2025) กำหนด "binding code" สำหรับผูกอุปกรณ์ใหม่ไว้ชัดเจนว่าต้องยาว **≥112 bit ถ้าไม่มี identifier ที่พิมพ์ก่อนหน้า หรือ ≥40 bit ถ้าใช้คู่กับ username ใช้ได้ครั้งเดียว และอายุไม่เกิน 10 นาที** ส่งด้วยมือหรือ QR และต้องแจ้ง subscriber ผ่านช่องทางที่แยกจาก transaction ([NIST 63B-4: Events](https://pages.nist.gov/800-63-4/sp800-63b/events/)) ข้อเสนอคือให้ `user add`/`user pair <name>` ใน console และหน้า Admin ในแอปแสดง QR ที่บรรจุ server-id, endpoint list, SPKI SHA-256 และ secret 128 bit อายุ 10 นาที client สแกนแล้ว**ตรวจ pin ก่อนส่งข้อมูลใด ๆ ออกไป** ขั้น TOFU จึงหายไปทั้งขั้น และทุกครั้งที่มีการ pair ใหม่ อุปกรณ์อื่นของ user นั้นจะได้ event แจ้งเตือน ทางสำรองแบบพิมพ์มือใช้ username คู่กับ code ≥40 bit เช่น 10 ตัวจาก alphabet 20 ตัว `BCDFGHJKLMNPQRSTVWXZ` ของ RFC 8628 ได้ราว 43 bit จำกัด 5 ครั้งต่อ code ตามตัวอย่างใน RFC ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html)) และ**บังคับเทียบ fingerprint กับ console ก่อนส่ง code**

PAKE จะปิดช่องของ code แบบพิมพ์มือได้สนิทกว่า แต่ CPace ยังค้างอยู่ที่ RFC Editor ([IETF datatracker](https://datatracker.ietf.org/doc/draft-irtf-cfrg-cpace/)) และยังไม่พบ library ที่ audit แล้วซึ่งครอบทั้ง JVM, iOS และ Wasm แม้แต่ wrapper libsodium แบบ KMP ก็ยังประกาศตัวว่า "Experimental library!" ([ionspin](https://github.com/ionspin/kotlin-multiplatform-libsodium)) จึงเลื่อนไปไว้ใน Later สำหรับ staff สาขาไกล ทางที่ปลอดภัยกว่าคือให้โทรศัพท์ของผู้จัดการสาขาที่ pair แล้วแสดง QR ให้เครื่องใหม่ หลังผู้จัดการ re-auth ด้วย password ตาม ASVS 7.5.1 ([ASVS V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)) ผลคือ**ต้องตัด setup code 48 ชั่วโมงทิ้ง** และย้าย "QR pairing" จากหมวด Later ใน MASTER เข้ามาไว้ใน P07/P11/P12

Code ที่ redeem แล้วต้องได้แค่ **enrollment token ที่ใช้ตั้ง password (และ PIN) ได้อย่างเดียว** ไม่ใช่ session เต็ม เพราะ Nextcloud CVE-2026-45690 เกิดจาก session token ชั่วคราวที่ออกก่อน factor ที่สองเสร็จแล้วถูก replay ผ่าน HTTP Basic ได้ ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-45690/)) แต่ละ install ต้องสุ่ม deviceId ของตัวเอง และต้อง key session ด้วยคู่ (deviceId, userId) เพื่อให้ staff หลายคนใช้เครื่องร้านเดียวกันได้ client ของ Jellyfin ที่ส่ง DeviceId คงที่ทำให้การ login เครื่องที่สองเตะเครื่องแรกออก เพราะ server ยอมให้มี token ได้ตัวเดียวต่อ DeviceId ([Tributary #313](https://github.com/jm2/tributary/issues/313))

### Session สองชั้น, PIN รายคน และ backoff แทน lockout

สำหรับ server เดียวที่เก็บ state เป็น YAML นั้น JWT ให้แค่ภาระจัดการ key และ revoke ยาก ข้อเสนอคือ **opaque token 256 bit จาก CSPRNG เก็บที่ server เป็น SHA-256** (ASVS 7.2.3 กำหนดขั้นต่ำ 128 bit) และตรวจทุก request กับ map ใน memory ที่ load จาก `data/sessions/` ทำให้ revoke มีผลทันที ([ASVS V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)) ระบบจริงพลาดตรงนี้ซ้ำแล้วซ้ำอีก Jellyfin เพิ่งพบในปี 2026 ว่าการเพิกถอนสิทธิ์อุปกรณ์ "would only ever have been re-evaluated when a user was renamed" ([jellyfin PR #17845](https://github.com/jellyfin/jellyfin/pull/17845)) P07 มี "Disable user → token ใช้ไม่ได้ + WS หลุดทันที" แล้ว ต้องขยายให้ครอบการเปลี่ยน password การเปลี่ยน role และการ revoke device ด้วย ฝั่ง client ให้เก็บ device secret ใน Keychain class `…ThisDeviceOnly` ซึ่งไม่ขึ้น iCloud Keychain และไม่ถูก restore ไปเครื่องใหม่ ([Apple: Keychain access control](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id.md)) ส่วนบน Android ทางเลือก Keystore + DataStore ใน plan ถูกแล้ว เพราะ `EncryptedSharedPreferences` ถูก deprecate ไปตั้งแต่ มิ.ย. 2025 ([AndroidX Security](https://developer.android.com/jetpack/androidx/releases/security))

"Session 30 วัน rolling" ขัดทั้ง NIST และ ASVS เพราะ AAL1 ต้องมี **overall reauthentication timeout ที่แน่นอนและควรไม่เกิน 30 วัน** ([NIST 63B-4: AAL](https://pages.nist.gov/800-63-4/sp800-63b/aal/)) ขณะที่ ASVS 7.3.2 ต้องมี absolute maximum lifetime ซึ่ง session แบบ rolling ล้วนไม่เคยบังคับให้ reauth เลย การปล่อยยาวเกินไปก็พังเหมือนกัน cookie 400 วันของ Immich ทำให้ผู้ใช้ login ค้างบนเครื่องที่ครอบครัวใช้ร่วมกัน ([Immich #13318](https://github.com/immich-app/immich/discussions/13318)) ข้อเสนอคือแยกเป็นสองชั้น ชั้น **pairing** อยู่จนถูก revoke หรือไม่ถูกใช้ 90 วัน ซึ่งเป็นกติกาเดียวกับ refresh token ของ Home Assistant ตั้งแต่ 2024.2 ([HA PR #108428](https://github.com/home-assistant/core/pull/108428)) ส่วนชั้น **session** ต้องยืนยัน password ซ้ำเมื่อครบ 30 วันนับจากครั้งล่าสุดที่กรอก หรือเมื่อว่างเกิน 14 วัน โดยไม่ต้องขอ QR ใหม่ และไม่ใช่การบังคับเปลี่ยน password ซึ่ง NIST ห้าม ในทางกลไก device secret ใช้ได้กับ endpoint unlock เท่านั้น แล้วแลกเป็น access token อายุ ≤15 นาทีที่อยู่ใน memory จุดแลกจุดเดียวนี้คือที่ที่จะเพิ่ม device keypair ได้ภายหลังเพื่อให้ credential เป็น sender-constrained ตามที่ RFC 9700 บังคับกับ refresh token ของ public client ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html))

เครื่องที่ใช้ร่วมกันต้องแยก "อนุญาตอุปกรณ์" ออกจาก "ใครกำลังใช้" แบบที่ POS ทุกเจ้าทำ Loyverse ให้ login เต็มแค่ครั้งแรกเพื่อผูกพนักงานกับเครื่อง แล้วใช้ PIN ตอนปลดล็อก ([Loyverse](https://help.loyverse.com/help/how-give-employees-access-login)) Toast ตั้ง idle timeout ได้ต่ำถึง 5 วินาที ([Toast](https://support.toasttab.com/en/article/Adjust-POS-Screen-Timeout)) และ Square เตือนว่า team passcode ที่ใช้ร่วมกัน **"does not support the ability to track time, sales, or activity by team member"** ([Square](https://squareup.com/help/us/en/article/8357-require-passcodes-at-point-of-sale)) ซึ่งทำลาย audit trail ของ ledger Biometrics ใช้บนเครื่องร่วมไม่ได้ เพราะแอปรู้แค่ว่าสแกน "สำเร็จ" ไม่รู้ว่าเป็นนิ้วของใคร ([Apple Platform Security](https://support.apple.com/guide/security/uses-for-face-id-and-touch-id-secc5227ff3c/1/web))

ข้อเสนอคือ **PIN 6 หลักรายคน** ตาม NIST ที่ให้ activation secret ยาว ≥4 ตัวแบบ SHALL และ ≥6 ตัวแบบ SHOULD และต้องปิดเมื่อผิด ≤10 ครั้ง ([NIST 63B-4: Authenticators](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)) client ส่ง PIN ไปตรวจที่ server ผ่านช่องที่ pin แล้ว server เก็บ Argon2id(PIN) และนับครั้งผิดต่อคู่ (user, device) ผิดครบ 10 ครั้งจะ revoke credential ของ user นั้นบนเครื่องนั้น เพราะตัวนับฝั่ง client ถูก reset ได้บนเครื่องที่ root หรือ jailbreak เมื่อ server ไม่อยู่ (โหมด outbox) ให้ตรวจ PIN กับ hash ในเครื่องได้เฉพาะการสร้าง entry และติด flag ใน history ส่วน sync รอ unlock ครั้งถัดไปที่ server ตรวจได้ ข้อนี้ต้องบันทึกเป็น deviation โดยตั้งใจ เพราะ NIST นับ secret ที่ส่งไป server เป็น password (≥8 ตัว) และ PIN 6 หลักบนเครื่องที่ถูก root เดาได้ แอป lock หลังว่าง 2–5 นาทีบนเครื่องหน้าร้าน ซึ่งเป็นช่วงที่ OWASP ให้สำหรับแอปมูลค่าสูง ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)) ตั้งแยกต่อเครื่องผ่าน server-driven config และเปิด biometrics ได้เฉพาะเครื่องที่ mark ว่าเป็นของส่วนตัว

เมื่อ native client สร้าง session บนเครื่องใหม่ด้วย password อย่างเดียวไม่ได้แล้ว password ก็ไม่ใช่ factor เดียว NIST ให้ขั้นต่ำ **8 ตัวเมื่อเป็นส่วนหนึ่งของ MFA และ 15 ตัวเมื่อใช้เดี่ยว** ([NIST 63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)) จึงเสนอ 8 ตัวสำหรับ user ทั่วไป และ 15 ตัวสำหรับ `op` กับ account ที่จะ login web client โดย server ตรวจความยาวตอน login ทาง web ห้าม composition rule รับอย่างน้อย 64 ตัว normalize เป็น NFC ก่อน hash เพราะสระและวรรณยุกต์ลาวเป็น combining character ที่แป้นพิมพ์ต่างกันอาจเรียงต่างกัน และเทียบกับ blocklist อย่างน้อย top 3,000 ตาม ASVS 6.2.4 บวกคำเฉพาะร้าน เช่นชื่อร้าน ชื่อสาขา และ username ([ASVS V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)) Hash ด้วย Argon2id **m=46 MiB, t=1, p=1** ซึ่งเป็นหนึ่งในชุดที่ OWASP ให้ ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)) เก็บเป็น PHC string เพื่อเพิ่ม parameter ภายหลังได้ ใช้ semaphore จำกัดจำนวน hash พร้อมกันไม่ให้ login burst กิน RAM ของ PC เจ้าของร้าน ทำ rate-limit ก่อน hash และ hash หลอกเมื่อไม่มี username นั้นเพื่อให้เวลาตอบเท่ากัน

"Lockout (user + IP)" ใน P07 เป็นกับดักสองชั้น ชั้นแรก lockout แบบแข็งเปิดให้ใครก็ได้ที่รู้ username ล็อกเจ้าของออก Jellyfin เคยปิด account รวมถึง admin จนมีคนเขียนว่า **"you can be trapped away from your server by anyone who knows your username"** ([jellyfin #1076](https://github.com/jellyfin/jellyfin/issues/1076)) และ ASVS 6.1.1 บังคับให้เอกสารระบุว่ากัน malicious lockout อย่างไร ชั้นที่สอง IP ในลาวไม่ใช่ตัวแทนของคน เพราะ IP สาธารณะหนึ่งตัวอยู่หลัง CGNAT ของผู้ใช้มือถือจำนวนมาก (ส่วนที่ 3) และเมื่อใช้ relay ทุกคนจาก internet จะมาจาก IP เดียว เอกสาร Nextcloud เตือนว่า proxy ที่ตั้งค่าผิดทำให้ throttle traffic ทั้งหมดที่ผ่าน proxy ([Nextcloud brute force](https://docs.nextcloud.com/server/stable/admin_manual/configuration_server/bruteforce_configuration.html)) ข้อเสนอคือ token bucket ต่อ IP ด้วย `RateLimit` ของ Ktor ที่ตอบ 429 + `Retry-After` ([Ktor](https://ktor.io/docs/server-rate-limit.html)) คู่กับ exponential backoff ต่อ account ที่เริ่ม 1 วินาทีแล้วเพิ่มเท่าตัวจนเพดานราว 15 นาที ปิด authenticator เมื่อผิดติดกัน 100 ครั้งตามเพดานของ NIST แล้วปลดด้วย `user unlock` จาก console และ**ไม่มี automatic IP ban** โดย `ban-ip` ใช้มือเท่านั้น Pairing ยังลดพื้นผิวลงเองด้วย เพราะ endpoint ที่ไม่ต้องมี device credential เหลือแค่การ redeem code ซึ่งมีเพดานครั้งต่อ code กับ login ของ web client ที่เป็น LAN-only

การกระทำที่กระทบ credential หรือตัวเลข ได้แก่ เปลี่ยน password/PIN เพิ่มหรือ revoke device เปลี่ยน role หรือ `op` ลบหรือ void entry และ export ต้อง re-auth ด้วย password ภายในไม่กี่นาทีตาม ASVS 7.5.1 การกู้คืนที่ไม่มี email ให้ console เป็น root of trust โดย `user reset <name>` จะ revoke device ทั้งหมด ออก pairing ใหม่ และให้ user ตั้ง password เอง admin ไม่เคยเป็นผู้เลือก password ให้ (ASVS 6.4.6 ใน [ASVS V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)) Web client ซึ่งถือ device secret ไม่ได้ใช้ password คู่กับ cookie `__Host-` ที่ตั้ง `Secure; HttpOnly; SameSite=Strict; Path=/` ตามที่ NIST แนะนำ ([NIST 63B-4: Session](https://pages.nist.gov/800-63-4/sp800-63b/session/)) โดยอายุสั้นกว่า native เช่น absolute 12 ชั่วโมงและ idle 30 นาที ยังไม่มีหลักฐานว่า `__Host-` cookie ใช้ได้บน host ที่เป็น IP และ cookie อยู่รอดบนหน้า cert error หรือไม่ จึงต้องทดสอบใน P11

### Passkeys ตกรอบเพราะ IP, self-signed และ AltStore

Passkeys/WebAuthn **ใช้ไม่ได้ภายใต้ข้อจำกัดของ BCN** และไม่ควรเสียเวลาทดลอง Spec บังคับให้ RP ID เป็น domain โดยตั้งใจตัด IP ออก และเปิด API เฉพาะเมื่อ TLS "established without errors" ([W3C WebAuthn L3](https://www.w3.org/TR/webauthn-3/)) Chrome บล็อก WebAuthn บนเว็บที่ cert error ตั้งแต่ M110 ([Chromium](https://lists.w3.org/Archives/Public/public-webauthn/2022Nov/0135.html)) และ Firefox ปิดช่องเดียวกันใน 140 (CVE-2025-6433 ใน [Mozilla MFSA 2025-51](https://www.mozilla.org/en-US/security/advisories/mfsa2025-51/)) ส่วน iOS ต้องใช้ Associated Domains ซึ่ง **personal team ที่ AltStore ใช้ไม่รองรับ** ([Flutter docs](https://docs.flutter.dev/cookbook/navigation/set-up-universal-links)) และไฟล์ AASA ต้องให้ CDN ของ Apple ดึงผ่าน cert ที่ valid ([Apple: Associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains.md)) ให้บันทึกใน MASTER ว่า "rejected จนกว่าจะมี public domain + paid Apple account" คุณสมบัติที่ passkey ให้ คือ key ที่ผูกกับ hardware และกัน phishing ได้มาแทนด้วย device keypair P-256 ใน Secure Enclave, Keystore หรือ TPM ที่เซ็น challenge รวม SPKI hash ของ server งานนี้เป็น hardening หลัง v1 แต่ควรสำรอง field `device-key` ไว้ใน session file ตั้งแต่ตอนนี้

## AltStore ไหวเฉพาะ iPhone ไม่กี่เครื่องที่มี AltServer เปิดทุกสาขา

AltStore Classic รุ่นปัจจุบันคือ **2.3 ที่ออกวันที่ 14 ก.ย. 2026 วันเดียวกับ iOS 27 และยกขั้นต่ำเป็น iOS 17.4** ([AltStore release notes](https://faq.altstore.io/release-notes/altstore)) โดย release notes ไม่มีบรรทัดยืนยันว่ารองรับ iOS 27 ดังนั้น "Min: iOS 14" ใน MASTER Stack จึงไม่มีผลกับช่องทางนี้ floor ที่ต้องทดสอบจริงคือ 17.4 ซึ่ง iPhone 11 ขึ้นไปผ่านทั้งหมดเพราะรัน iOS 27 ได้ ([MacRumors](https://www.macrumors.com/2026/09/09/apple-announces-ios-27-release-date/)) เงื่อนไขของ Apple ID ฟรียังเหมือนเดิม คือแอป**หมดอายุทุก 7 วัน** sideload ได้ **3 แอปต่อเครื่องโดย AltStore นับเป็นหนึ่งในนั้น** ([AltStore: Getting Started](https://faq.altstore.io/altstore-classic/your-altstore)) ลง App ID ได้ 10 ตัวต่อ 7 วัน ([AltStore: App IDs](https://faq.altstore.io/altstore-classic/app-ids)) ซึ่ง BCN ที่ไม่มี app extension ใช้ตัวเดียว ([InstalledApp.swift](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStoreCore/Model/InstalledApp.swift)) และต้องเปิด **Developer Mode** ทุกเครื่อง เพราะ Apple บังคับกับแอปที่เซ็นด้วย Personal Team ขณะที่ TestFlight, Enterprise และ App Store ไม่ต้อง ([WWDC22: Developer Mode](https://developer.apple.com/videos/play/wwdc2022/110344/))

ความเสี่ยงหลักในงานประจำวันคืออายุ 7 วัน ทุกเครื่องต้องเจอ AltServer บน Wi-Fi เดียวกันอย่างน้อยสัปดาห์ละครั้ง และ AltStore เองแนะนำให้เปิด AltServer ตั้งแต่เครื่องบูตแล้วปล่อยไว้ ([AltServer](https://raw.githubusercontent.com/altstoreio/FAQ/main/altstore-world/altserver.md)) AltServer บน Windows ต้องลง iTunes และ iCloud จากเว็บ Apple ไม่ใช่จาก Microsoft Store และ Wi-Fi ที่กันไม่ให้อุปกรณ์เห็นกันจะทำให้ refresh ไม่ได้ ([AltStore troubleshooting](https://raw.githubusercontent.com/altstoreio/FAQ/main/altstore-world/troubleshooting-guide.md)) แปลว่า**ทุกสาขาที่มี iPhone ต้องมี Mac หรือ PC เปิดตลอด** ซึ่งในสาขาหลักใช้เครื่องเดียวกับที่รัน `bcn-server.jar` ได้ Remote AltServer ใน 2.3 ตัดคอมพิวเตอร์ออกได้ แต่ต้องใช้ Wi-Fi (ไม่ใช่ cellular) คู่กับ LocalDevVPN และเอกสารยอมรับว่า remote server อาจ "currently unavailable" ([AltStore: Remote AltServers](https://faq.altstore.io/altstore-classic/remote-altservers)) มี issue ที่ยังเปิดอยู่ว่าตั้งค่าไม่ได้บน iPhone 18 Pro ตั้งแต่ 19 ก.ย. 2026 ([AltStore #1811](https://github.com/altstoreio/AltStore/issues/1811)) และไม่มีเอกสารว่าใครรัน server เหล่านั้นหรือได้ข้อมูลอะไรไป ซึ่งขัดหลักไม่พึ่ง server ของคนอื่น จึงเป็นได้แค่ pilot ส่วน SideStore ใช้กลไกเดียวกัน แต่เอกสารของเขาเองบอกว่า pairing file หมดอายุได้หลังอัปเดต iOS และ "at random times" ([SideStore: Pairing file](https://docs.sidestore.io/docs/advanced/pairing-file)) จึงไม่แนะนำ

ความเสี่ยงที่สร้างขึ้นเองได้ง่ายที่สุดคือใช้ Apple ID เดียวหลายเครื่อง AltStore จะ revoke cert ที่หา private key ไม่เจอแล้วสร้างใหม่ ทำให้เครื่องอื่นพังวนเป็น loop ซึ่งทางแก้คือแยก Apple ID ([AltStore #1597](https://github.com/altstoreio/AltStore/issues/1597)) และ AltStore เองแนะนำให้สร้าง Apple ID เฉพาะสำหรับ sideload ([AltStore troubleshooting](https://raw.githubusercontent.com/altstoreio/FAQ/main/altstore-world/troubleshooting-guide.md)) เนื่องจาก AltStore ต้องใช้ password จริงบวกรหัส 2FA 6 หลัก ([AuthenticationOperation.swift](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStore/Operations/AuthenticationOperation.swift)) ข้อเสนอจึงเป็น **Apple ID ของร้านหนึ่งตัวต่อ iPhone หนึ่งเครื่อง** ที่ผูก 2FA กับเบอร์ของเจ้าของร้าน และห้ามใช้ Apple ID ของนักพัฒนา อีกข้อคือ**งดอัปเดต iOS บนเครื่องร้านจนกว่า AltStore จะยืนยันว่ารองรับ** เพราะ iOS 26.4 ทำให้ AltStore ที่ติดตั้งผ่าน AltServer for Windows เปิดแล้วจอดำและ crash ([AltStore #1730](https://github.com/altstoreio/AltStore/issues/1730)) กว่าจะแก้ใน AltServer 1.7.4 ก็ถึงวันที่ 24 มี.ค. 2026 ([AltServer release notes](https://faq.altstore.io/release-notes/altserver)) หลังเริ่มมีรายงานตั้งแต่ช่วง beta เดือน ก.พ.

ตัวแอปต้องออกแบบรับพฤติกรรมของ AltStore สามข้อ ข้อแรก AltStore เปลี่ยน bundle ID เป็น `<bundleID>.<TEAMID>` ตอนเซ็นใหม่ ([FetchProvisioningProfilesOperation.swift](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStore/Operations/FetchProvisioningProfilesOperation.swift)) จึงห้ามใช้ bundle ID ใน logic หรือเพื่อระบุตัวตนที่ server และห้าม hard-code `kSecAttrAccessGroup` ข้อสอง refresh 7 วันแค่ติดตั้ง provisioning profile ใหม่ ([RefreshAppOperation.swift](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStore/Operations/RefreshAppOperation.swift)) ข้อมูลและ Keychain จึงอยู่รอด แต่การเปลี่ยน Apple ID หรือ team ทำให้ Keychain หายหนึ่งครั้งตาม Apple QA1726 ([QA1726](https://developer.apple.com/library/archive/qa/qa1726/_index.html)) และการ deactivate/activate สำรองแค่ Documents กับ Library ไม่รวม Keychain ([BackupController.swift](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltBackup/BackupController.swift)) จึงต้องออกแบบให้ server เป็นตัวจริง ให้ re-pair มีต้นทุนต่ำ และให้ outbox ส่งหมดก่อนตั้งเครื่องใหม่ ข้อสาม ไม่ต้องขอ entitlement ใดเลย เพราะ Bonjour สำหรับ service type ที่ประกาศไว้ใช้แค่ `NSLocalNetworkUsageDescription` + `NSBonjourServices` ส่วน multicast entitlement จำเป็นเฉพาะ raw multicast หรือการ browse ทุก type ([TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)) และ AltStore เองก็หา `_altserver._tcp` ด้วยสองคีย์นี้ ([AltStore Info.plist](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStore/Info.plist)) อย่างไรก็ตาม personal team **ไม่รองรับ Push Notifications** ([Apple Forums 718388](https://developer.apple.com/forums/thread/718388)) แจ้งเตือนบน iOS จึงมาได้แค่ทาง WS ขณะเปิดแอปหรือทาง Telegram plugin และ TN3179 ยังเตือนว่า local network prompt ครั้งแรกอาจ deny request ทันทีก่อนผู้ใช้ตอบ client จึงต้องมี retry

CI ใน P00 ทำได้ตามแผน Xcode run script เรียก `embedAndSignAppleFrameworkForXcode` ([Kotlin docs](https://kotlinlang.org/docs/multiplatform/multiplatform-direct-integration.html)) ตามด้วย `xcodebuild archive` แบบปิด signing แล้ว zip `Payload/` เป็น `.ipa` ให้ AltStore เซ็นบนเครื่อง แต่ยังไม่มีใครยืนยันว่า script ของ Kotlin ทำงานปกติเมื่อตั้ง `CODE_SIGNING_ALLOWED=NO` จึงต้องให้ P00 พิสูจน์ การอัปเดตใน P13 ต้องไม่ใช้ deep link `altstore://install?url=` เพราะ AltStore **ไม่มี ATS exception** ([AltStore Info.plist](https://raw.githubusercontent.com/altstoreio/AltStore/master/AltStore/Info.plist)) และจะโหลดจาก server self-signed ของ BCN ไม่ได้ ทางที่ทนที่สุดคือให้ BCN ดาวน์โหลด `.ipa` ผ่านช่องที่ pin แล้วเปิด share sheet ส่งให้ AltStore ซึ่งลงทะเบียน document type `com.apple.itunes.ipa` ไว้แล้ว โดยขั้นติดตั้งยังต้องเห็น AltServer อยู่ดี วิธีนี้ไม่ต้องมี AltStore source บน GitHub และถ้าวันหนึ่งใช้ source ต้องประกาศ entitlement และ privacy string ให้ตรงกับ `.ipa` ทุกตัว มิฉะนั้น AltStore จะปฏิเสธการติดตั้ง ([Make a Source](https://faq.altstore.io/developers/make-a-source.md))

## ร้านในลาวต้องสมมติว่าอยู่หลัง CGNAT ตั้งแต่วันแรก

ไม่มี ISP ลาวรายไหนเผยแพร่นโยบาย CGNAT ราคา static IP หรือการบล็อก inbound port หน้า FTTH ของ LTC แสดงแพ็กเกจ 35 Mbps ที่ 165,000 กีบ/เดือน แต่ไม่พูดถึง public IP เลย ([LTC FTTH](https://www.laotel.com/la/shop-LTC-FTTH.php?Lang=en)) ถึงอย่างนั้น ตัวเลข address ก็บอกคำตอบได้เกือบแน่นอน ลาวมี **IPv4 116,268 address** ([ipinfo](https://ipinfo.io/countries/la)) สำหรับผู้ใช้เน็ต **5.03 ล้านคน** และ fixed broadband **208,504** ราย ([Internet In Laos](https://www.internetlaos.com/2026/08/internet-providers-in-laos-compared-2026.html)) ต่อให้ยก IPv4 ทั้งประเทศให้ fixed line ก็ยังได้ราว 1.8 subscription ต่อ address และ Unitel ที่ครองตลาดราว 53% ถือ address แค่ 14,336 ตัว ([ipinfo](https://ipinfo.io/countries/la)) mobile CGNAT จึงแทบแน่นอน IPv6 ไม่ใช่ทางออก เพราะผู้ใช้ในลาวเข้าถึงผ่าน IPv6 ได้**ไม่ถึง 1%** ([ISOC Pulse](https://pulse.internetsociety.org/en/reports/LA/)) CGNAT มีผลเฉพาะกับสายที่ server อยู่ โทรศัพท์บน 4G ยังเชื่อมต่อออกไปหา server ได้ปกติ แต่ไฟดับบ่อยตามที่รายงานของรัฐบาลสหรัฐระบุ ([trade.gov](https://www.trade.gov/country-commercial-guides/laos-digital-economy)) ทำให้ router reboot และ IP เปลี่ยนได้ "เช็ค CGNAT" ใน README ของ P13 จึงต้องเป็นขั้นแรกของการติดตั้ง ไม่ใช่หัวข้อเสริม

ลำดับที่เสนอมีสามชั้น **ชั้นแรกคือ public IPv4 + port forward พอร์ตเดียว** อ่าน WAN address ของ router ที่ server อยู่ข้างหลัง ถ้าอยู่ใน `100.64.0.0/10` คือ CGNAT ([RFC 6598](https://www.rfc-editor.org/rfc/rfc6598)) ถ้าเป็น RFC1918 คือ double NAT จาก ONT ของ ISP ที่อยู่ใน router mode ซึ่งแก้ด้วย bridge mode หรือ DMZ และถ้าเป็น public ก็ forward พอร์ตสูง เช่น 8443 ไปยัง HTTPS listener ตัวเดียว ตรงกับ decision "HTTPS พอร์ตเดียว" ให้ทดสอบจากโทรศัพท์ของเจ้าของร้านที่ปิด Wi-Fi ใช้ 4G (ทดสอบจาก Wi-Fi ร้านใช้ไม่ได้เพราะ hairpin NAT ไม่แน่นอน) และถือว่าผ่านเมื่อ fingerprint ตรงกับที่ console แสดง ซึ่งไม่ต้องพึ่งเว็บ "what is my IP" ถ้า WAN ไม่ใช่ public ให้ขอ ISP เป็น "public IP" หรือ "fixed IP" ซึ่งน่าจะเป็นแพ็กเกจธุรกิจที่ไม่เปิดราคา DDNS เป็น optional โดยใช้ domain ของเจ้าของร้านบน DNS host ที่มี update API เช่น deSEC ที่ตั้ง TTL 60 วินาทีและตรวจ IP ผู้เรียกให้อัตโนมัติ ([deSEC](https://desec.readthedocs.io/en/latest/dyndns/update-api.html)) DNS host ช่วยแค่ "หา" ไม่เคยแตะข้อมูล แต่หลัง CGNAT การตรวจ IP อัตโนมัติจะประกาศ address ร่วมที่ใช้ต่อเข้าไม่ได้ server เรียนรู้ WAN IP จาก router เองได้ผ่าน PCP/NAT-PMP/UPnP ([RFC 6887](https://www.rfc-editor.org/rfc/rfc6887)) แต่ library Java ที่ครอบทั้งสามออกรุ่นล่าสุดเมื่อ ม.ค. 2023 และ router หลายรุ่นไม่ยอม map พอร์ต ≤1024 ([portmapper](https://github.com/offbynull/portmapper/blob/master/README.md)) UPnP จึงอยู่ใน Later ต่อไปได้

**ชั้นที่สองสำหรับร้านที่อยู่หลัง CGNAT คือ relay ที่เจ้าของร้านคุมเอง** ใช้ VPS ราคาถูก เช่น DigitalOcean ที่เริ่ม US$4/เดือนและมี region สิงคโปร์ ([DigitalOcean](https://www.digitalocean.com/pricing/droplets)) หรือ VPS ในลาวอย่าง AP Network ที่ไม่เปิดราคา ([AP Network](https://apnetwork.la/)) รัน reverse tunnel แบบ TCP passthrough เช่น rathole ซึ่งเป็น Apache-2.0 มี token ต่อ service รองรับ Noise/TLS และ binary ราว 500 KiB ([rathole](https://github.com/rathole-org/rathole)) หรือ frp ([xTom comparison](https://xtom.com/blog/frp-rathole-ngrok-comparison-best-reverse-tunneling-solution/)) หรือ WireGuard + DNAT ที่ฝั่งร้านตั้ง keepalive 25 วินาที ([WireGuard](https://www.wireguard.com/quickstart/)) จุดสำคัญคือ TLS ไป terminate ที่ `bcn-server.jar` **VPS จึงเห็นแค่ ciphertext และ SPKI pin ไม่เปลี่ยน** ส่วน address ของ relay เป็นแค่ endpoint อีกตัวใน list ของ client ตัวเลือกยอดนิยมอื่นขัดหลักทั้งหมด Cloudflare Tunnel สร้าง connection ขาออกไปยัง network ของ Cloudflare ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)) ทำให้บุคคลที่สามอยู่ใน path Headscale ใช้ DERP map ของ Tailscale เป็น default และปิด embedded DERP ไว้ ([Headscale config](https://raw.githubusercontent.com/juanfont/headscale/main/config-example.yaml)) อีกทั้งทุกเครื่องของ staff ต้องลงแอป Tailscale และ ZeroTier ก็ย้าย network controller ไปใช้ license เชิงพาณิชย์ใน 1.16 ([ZeroTier 1.16](https://docs.zerotier.com/changelog/2025/08/21/zt1-v1.16.0/)) **ชั้นที่สามคือไม่มี remote access** ใช้ LAN-only คู่กับ client outbox ที่ออกแบบไว้แล้ว staff สร้าง entry ได้ตอนอยู่นอกร้านแล้ว sync เมื่อกลับเข้า Wi-Fi แต่ดู dashboard และ records จากข้างนอกไม่ได้

เพื่อให้ decision นี้ lock ได้ ต้องเขียนหลัก "Own server" ใหม่ให้ตรงกับที่ plan ทำจริง plan ship Telegram plugin เป็น channel default ซึ่งส่งข้อมูล entry ออกไปนอกเครื่องอยู่แล้ว หลักที่ plan ใช้จริงจึงเป็น "source of truth, key และ account ไม่อยู่นอกโฟลเดอร์ jar ส่วนท่อภายนอกเป็น optional และเปลี่ยนเจ้าได้" relay, DNS และบริการ provisioning ของ Apple ที่ AltStore ต้องใช้ ล้วนอยู่ในหมวดนี้

### Relay ทำให้ internet กลายเป็น loopback

MASTER นิยาม LAN ว่า "RFC1918, loopback, link-local, IPv6 ULA + subnet ของ interface server" และใช้นิยามนี้ตัดสินทั้ง web client และ cookie เมื่อเปิด relay ตัว rathole/frp client ที่รันบนเครื่อง server จะส่งต่อ connection มาจาก 127.0.0.1 ส่วน WireGuard ที่ทำ SNAT จะส่งมาจาก address ของ tunnel ซึ่งมักเป็น RFC1918 ผลคือ**ทุก request จาก internet จะถูกนับเป็น LAN** web client จะถูกเสิร์ฟออก internet และ cookie จากนอกร้านจะถูกยอมรับ ขัดกับ decision "Web client = LAN only" ตรง ๆ และพร้อมกันนั้น per-IP throttling จะเห็นทุกคนเป็น IP เดียว นี่คือความล้มเหลวประเภทเดียวกับที่ Home Assistant เจอเมื่อ trusted network ถูกข้ามด้วย `X-Forwarded-For` ปลอม ([HA #14345](https://github.com/home-assistant/core/issues/14345)) และปัจจุบัน HA บล็อก request จาก reverse proxy ถ้าไม่ได้ตั้ง `trusted_proxies` ([HA HTTP](https://www.home-assistant.io/integrations/http/)) ข้อเสนอคือเพิ่ม config `relay-sources` ใน `server.properties` ให้ address ในรายการถูกนับเป็น internet เสมอ รวมถึง loopback เมื่อ relay เปิดอยู่ ยกเว้น address เหล่านี้จาก per-IP limit แล้วพึ่ง per-account backoff แทน และถ้า tunnel ที่เลือกรองรับ ให้รับ client IP จริงผ่าน PROXY protocol เฉพาะจาก relay ที่ประกาศไว้ ระยะยาวทางที่สะอาดที่สุดคือโหมด relay ของ BCN เอง ให้ server dial ออกไปหา `bcn-relay.jar` บน VPS แล้ว relay splice TLS byte ดิบของ client เข้ามา connection ที่มาทางนี้จะเป็น internet โดยโครงสร้างและพก client IP มาในเฟรมได้ แนวคิดนี้ยังไม่มีใครสร้าง จึงควรอยู่ใน Later

ฝั่ง client, P11 มี "1 server หลาย address · เจอ LAN ใช้ก่อน" อยู่แล้ว ต้องเพิ่มกติกาว่า**รับ endpoint ใดก็ได้ที่ยื่น key ตรงกับ pin** โดยถือว่า mDNS เป็นแค่ hint ให้ server ส่ง endpoint ใหม่ผ่าน `GET /api/v1/config` และ WS ทุกครั้งที่ WAN IP เปลี่ยน เช่นหลังไฟดับ และเก็บ backup pin ของ key ถัดไปไว้ล่วงหน้า Android เตือนว่าถ้าไม่มี backup pin ต้องออกแอปใหม่เพื่อกู้การเชื่อมต่อหลังเปลี่ยน key ([Android NSC](https://developer.android.com/privacy-and-security/security-config)) และ Apple แนะนำให้ pin ชุดของ key หรือ CA เพื่อให้หมุนได้ ([Apple: Manual server trust](https://developer.apple.com/documentation/foundation/performing-manual-server-trust-authentication)) Let's Encrypt ออก cert ให้ IP ได้แล้วตั้งแต่ 15 ม.ค. 2026 แต่ต้องเป็น profile shortlived 160 ชั่วโมง และ validate ได้แค่ผ่านพอร์ต 80 หรือ 443 ([Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)) จึงทำไม่ได้หลัง CGNAT และหมดอายุถ้าไฟดับเกินราว 6 วัน เมื่อ iOS ใช้ ATS exception คู่กับ pin แล้ว (ส่วนถัดไป) ACME ก็ไม่จำเป็นใน v1 ส่วน IPv6 ให้ listen แบบ dual-stack และใส่ global address ลง endpoint list เพราะไม่มีต้นทุน แต่ห้ามพึ่ง

## สาม decision ทำไม่ได้ตามที่เขียน: ATS, Configurate และ tmpdir

**ข้อที่หนักที่สุดคือ iOS** Ktor Darwin engine ทำงานบน URLSession ซึ่งอยู่ใต้ ATS และ Apple เขียนไว้ชัดว่าเมื่อ ATS เปิด **"you can no longer loosen trust evaluation requirements"** การยอมรับ cert self-signed จึงทำไม่ได้ ทำได้แค่เข้มขึ้น ([Apple: Preventing Insecure Network Connections](https://developer.apple.com/documentation/security/preventing-insecure-network-connections)) Quinn จาก Apple DTS สรุปว่าถ้าจะคุยกับ server self-signed "you must disable ATS for that server" ([Apple Forums 53314](https://developer.apple.com/forums/thread/53314)) และตั้งแต่ iOS 17 ATS ไม่ยอมให้ต่อ IP address โดย default ([NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking)) P11 ตั้ง Info.plist ไว้แค่ `NSLocalNetworkUsageDescription` + `NSBonjourServices` ซึ่งไม่ใช่ ATS exception และทั้ง plan ไม่มี ATS exception ที่ไหนเลย TOFU + pin ตามที่เขียนจึง**ต่อไม่ติดทั้งทาง LAN และทาง internet** ข้อเสนอให้ lock คือใส่ **`NSAllowsArbitraryLoads = YES` เพียงตัวเดียว** ห้ามใส่ `NSAllowsLocalNetworking` คู่กัน เพราะตั้งแต่ iOS 10 ระบบจะ ignore ArbitraryLoads ทันทีที่มีคีย์นั้น ([NSAllowsArbitraryLoads](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowsarbitraryloads)) คีย์นี้ครอบทั้ง LAN IP, public IP, domain ของเจ้าของร้าน และ relay ส่วน App Review justification ที่คีย์นี้ต้องใช้ไม่เกี่ยวกับ AltStore หรือ ad hoc และจะกลับมาเป็นประเด็นเฉพาะเมื่อขึ้น App Store หรือ TestFlight external ทางเลือกที่ใช้ `NSAllowsLocalNetworking` แล้วให้ internet path ใช้ cert สาธารณะต้องพึ่ง ACME ซึ่งติด CGNAT ตามส่วนที่แล้ว

การ implement ต้องใช้ `handleChallenge` ของ Ktor Darwin เทียบ SPKI แล้วตอบ `UseCredential` เฉพาะเมื่อตรง นอกนั้นตอบ `Cancel` และห้าม fall through ไป `PerformDefaultHandling` โปรเจกต์ KMP ที่ใช้ Ktor 3.4.3 ยืนยันว่า handler นี้ถูกเรียกกับ `NSURLSessionWebSocketTask` ด้วย `wss://` จึงถูกครอบไปด้วย ([CivitDeck #1128](https://github.com/rioX432/CivitDeck/issues/1128)) ห้ามใช้ preconfigured session เพราะ Ktor จะ ignore `handleChallenge` แบบเงียบ ๆ ([DarwinClientEngineConfig.kt](https://github.com/ktorio/ktor/blob/main/ktor-client/ktor-client-darwin/darwin/src/io/ktor/client/engine/darwin/DarwinClientEngineConfig.kt)) และไม่ควรใช้ `CertificatePinner` ของ Darwin ที่ออกแบบมาสำหรับ cert จาก CA ([CertificatePinner.kt](https://github.com/ktorio/ktor/blob/main/ktor-client/ktor-client-darwin/darwin/src/io/ktor/client/engine/darwin/certificates/CertificatePinner.kt)) เมื่อปิด ATS แล้ว pin คือการป้องกันชั้นเดียวที่เหลือ Quinn เตือนว่าการใช้ `.useCredential` ในแอปที่ปิด ATS แล้วไม่ตรวจเองนั้น "you'd have no protection at all" ([Apple Forums 749633](https://developer.apple.com/forums/thread/749633)) กฎ "no cleartext" จึงต้องย้ายไปบังคับใน client code ให้ใช้ key ECDSA P-256 ทุกที่ เพราะ public key ที่ iOS คืนมาไม่มี ASN.1 header ต้องเติมก่อนจึงจะได้ SPKI hash ตรงกับ JVM/Android และ P-256 มี header คงที่แบบเดียว เอกสาร Apple ยังขัดกันเองว่า IP literal ต้องใส่ `NSExceptionDomains` ราย IP เพิ่มหรือไม่ DTS บอกให้ใส่ ([Apple Forums 747421](https://developer.apple.com/forums/thread/747421)) ขณะที่หน้า `NSAllowsLocalNetworking` บอกว่าคีย์นั้นครอบ IP แล้ว ข้อนี้จึงต้องผ่าน device test ก่อน lock

### ความเสี่ยงที่เหลือแก้ได้ภายใน phase ของมัน

**Cert (P07)** `generateCertificate()` ของ Ktor ให้ SHA1withRSA 1024 bit อายุ 3 วัน `CertificateBuilder` รับ key pair เดิมไม่ได้ และ Netty สร้าง `SslContext` ครั้งเดียว ([Certificates.kt](https://github.com/ktorio/ktor/blob/main/ktor-network/ktor-network-tls/ktor-network-tls-certificates/jvm/src/io/ktor/network/tls/certificates/Certificates.kt), [NettyChannelInitializer.kt](https://github.com/ktorio/ktor/blob/main/ktor-server/ktor-server-netty/jvm/src/io/ktor/server/netty/NettyChannelInitializer.kt)) "ต่ออายุเองด้วย key เดิม" จึงต้องใช้ BouncyCastle และมีผลตอน restart ข้อเสนอที่ดีกว่าคือให้ first run สร้าง **private root CA (ECDSA P-256)** แล้วออก leaf อายุ ≤825 วัน ที่มี SAN เป็น iPAddress ของทุก LAN IP (ไม่ใช่ dNSName แบบในตัวอย่างของ Ktor) บวก `.local` และ domain และออกใหม่อัตโนมัติเมื่อ IP เปลี่ยน native client pin SPKI ของ CA ซึ่งเป็นแบบที่ DTS เรียกว่า "proper" ([Apple Forums 703234](https://developer.apple.com/forums/thread/703234)) และเครื่องหน้าร้านที่ใช้ web client เป็นหลักติดตั้ง CA ครั้งเดียวได้ ข้อแลกคือ root ที่ติดตั้งแล้วเซ็นได้ทุก domain ถ้า key หลุด จึงควรติดตั้งเฉพาะเครื่องของร้าน

**Storage บน Windows (P08)** เสี่ยงกว่าที่ "atomic write + fsync" ฟังดู `ATOMIC_MOVE` บน Windows คือ `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` ที่ไม่ส่ง `WRITE_THROUGH` ([WindowsFileCopy.java](https://github.com/openjdk/jdk/blob/1587398892ce98284c9c994b14696a96cd43e1ed/src/java.base/windows/classes/sun/nio/fs/WindowsFileCopy.java)) Microsoft ไม่ได้รับรองว่าเป็น atomic และแจ้ง error เมื่อปลายทางเป็น directory ที่มีอยู่แล้ว ([MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)) Java fsync directory บน Windows ไม่ได้ ([Lucene IOUtils](https://github.com/apache/lucene/blob/e357029271b3de560a6ff13c9cab4d4c8103b53b/lucene/core/src/java/org/apache/lucene/util/IOUtils.java)) และ rename จะ fail เป็นพัก ๆ เพราะ antivirus หรือ indexer ถือ handle อยู่ Go จึง retry rename ด้วย backoff ตั้งแต่ 1 ms ถึง 2 วินาที ([Go robustio](https://github.com/golang/go/blob/2ff5743d9fd52fac166225e75df0c2c1edf82abb/src/cmd/internal/robustio/robustio.go)) P08 ต้องเพิ่ม retry wrapper อ่านไฟล์ผ่าน NIO เท่านั้น เพราะ `java.io` ไม่เปิด `FILE_SHARE_DELETE` และจะทำให้ rename ของ writer เองพัง ([io_util_md.c](https://github.com/openjdk/jdk/blob/1587398892ce98284c9c994b14696a96cd43e1ed/src/java.base/windows/native/libjava/io_util_md.c)) เพิ่ม recovery scan ตอน start และตรวจชนิด filesystem เพื่อปฏิเสธ FAT32, exFAT และ network share "move date = rename โฟลเดอร์" คือ operation ที่เสี่ยงที่สุดและยังไม่มีใครทดสอบบน Windows ที่ Defender เปิดอยู่ ขณะที่ประสิทธิภาพที่ราว 100k โฟลเดอร์ ซึ่ง P09 ต้อง verify ก่อน `Done` ก็ยังไม่มีตัวเลข ถ้าต้องการความทนทานระดับที่พิสูจน์แล้ว ทางเลือกคือ journal แบบ append-only หรือ SQLite สำหรับ ledger ซึ่งงาน OSDI 2014 พบช่องโหว่ crash-consistency ใน SQLite น้อยกว่า Git และ Mercurial หลายเท่า ([Pillai et al.](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-pillai.pdf)) แต่ทางนี้ขัด decision "ไม่มี DB" จึงเสนอให้คงโฟลเดอร์ไว้และทดสอบบน Windows ก่อน

**Hotfix (P05)** ทำได้ เพราะ JEP 451 จำกัดเฉพาะ agent ที่ load แบบ dynamic ([JEP 451](https://openjdk.org/jeps/451)) และ Ignite ก็ใช้ `defineClass` ใน classloader ของตัวเองทำ Mixin บน Paper อยู่แล้ว ([Ignite EmberClassLoader](https://github.com/vectrix-space/ignite/blob/582cd741d46c943f5fb82a9b2eeb2ea4c8a80cb7/launcher/src/main/java/space/vectrix/ignite/launch/ember/EmberClassLoader.java)) แต่มีเงื่อนไขว่า core ต้องถูกโหลดผ่าน transforming loader ที่ P02 สร้างหลังจากอ่าน hotfix jar แล้ว hotfix ต้องอยู่ใน loader ของ core ไม่ใช่ loader แยกแบบ plugin ใน P04 และรายการ method ต้องห้ามต้องกว้างกว่า inline/suspend มาก เพราะ Kotlin mangle ชื่อ function ที่รับ value class ([Kotlin inline classes](https://kotlinlang.org/docs/inline-classes.html)) และ member ที่เป็น `internal` รวมถึงสร้าง method ซ้ำจาก `@JvmStatic` ([Kotlin–Java interop](https://kotlinlang.org/docs/java-to-kotlin-interop.html)) อีกทั้ง upstream SpongePowered Mixin หยุดอยู่ที่ commit ก.ค. 2024 ([SpongePowered Mixin](https://github.com/SpongePowered/Mixin/blob/4053421aa10aaac6127d969028a29c94fe3054f6/gradle.properties)) ข้อเสนอคือจำกัด target เฉพาะ method ที่ core ติด `@HotfixTarget` + `@JvmName` pin patch กับ SHA-256 ของ class เป้าหมาย ให้ injection ที่ match 0 จุดเป็น fatal และเลื่อน P05 ไปหลัง P13 เพราะ override ใน P04 ร่วมกับการออก core build ใหม่ครอบงานส่วนใหญ่ได้ แต่ให้ P02 ใช้ classloader class ของ BCN เองตั้งแต่ต้นเพื่อไม่ต้องรื้อ launcher ทีหลัง ส่วน **Plugin (P04)** นั้นการแชร์ Kotlin runtime จาก parent loader ถูกแล้ว แต่ binary compatibility ของ Kotlin ไปทางเดียว ([Kotlin evolution](https://kotlinlang.org/docs/kotlin-evolution-principles.html)) จึงต้องปฏิเสธ jar ที่มี `kotlin/` หรือ `kotlinx/` อยู่ข้างในและ plugin ที่ compile ด้วย Kotlin ใหม่กว่า host plugin ยังเป็น full trust และมัลแวร์ fractureiser ที่แพร่ผ่าน mod Minecraft ([fractureiser](https://github.com/fractureiser-investigation/fractureiser/blob/main/README.md)) เป็นเหตุผลให้ทำ SHA-256 allowlist ที่เจ้าของต้องยืนยันทุก jar ใหม่

**ฝั่ง client (P11)** บน Android `CertificatePinner` ของ OkHttp pin cert self-signed ไม่ได้ ([OkHttp](https://square.github.io/okhttp/4.x/okhttp/okhttp3/-certificate-pinner/)) ต้องเขียน `X509TrustManager` เองที่ throw เมื่อ SPKI ไม่ตรง คู่กับ HostnameVerifier ที่เช็ก pin แทนการคืน true เสมอ ซึ่ง Google Play บล็อกมาตั้งแต่ปี 2017 ([Google Play](https://support.google.com/faqs/answer/7188426)) Android 17 ที่ targetSdk 37 บล็อก LAN จนกว่าจะได้ `ACCESS_LOCAL_NETWORK` และ TCP จะ fail เป็น timeout เงียบ ๆ ([Android: Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)) P11 ขอ permission แล้วแต่ต้องเพิ่ม rationale screen หรือใช้ NSD picker ฝั่ง web client เมื่อ cert error Chromium ไม่ register service worker ([w3c/ServiceWorker #1514](https://github.com/w3c/ServiceWorker/issues/1514)) และไม่ cache response ([Peter Mekhaeil](https://www.petermekhaeil.com/til/chrome-certificates/)) header immutable/no-cache ใน P11 จึงมีผลเฉพาะเครื่องที่ติดตั้ง CA แล้ว ต้องมี SSE หรือ long-poll สำรองสำหรับ Safari ต้องบังคับ Safari 18.2+ ([Kotlin/Wasm](https://kotlinlang.org/docs/wasm-configuration.html)) และห้ามพึ่งการโหลด Noto อัตโนมัติของ Compose ที่ต้องใช้ internet ([Compose web resources](https://kotlinlang.org/docs/multiplatform/compose-web-resources.html)) ดังนั้นการ bundle font ลาว/ไทยใน P01 จึงถูกแล้ว jmDNS บน Windows ที่มี VPN หรือ Hyper-V ส่ง multicast ออกผิด interface ([jmdns #145](https://github.com/jmdns/jmdns/issues/145)) ต้องสร้าง instance ต่อ interface และเปิด firewall UDP 5353 สุดท้าย root path ภาษาลาว/ไทยใน Verify ของ P02 ชนกับ comment ใน JNA ที่ว่า `System.load` ใต้ directory ที่มีชื่อ unicode บน Windows จะ fail ([JNA Native.java](https://github.com/java-native-access/jna/blob/d036ad9781adad4b66693e8fa7098e4ac665e0a3/src/com/sun/jna/Native.java)) comment นี้อาจล้าสมัยแล้ว แต่ต้องทดสอบจริง

### ห้า device test ที่พลิก decision ได้

ก่อน lock มี device test ห้ารายการที่ผลของมันพลิก decision ได้ และควรทำใน P00 ก่อนเริ่มเขียน server จริง รายการแรกคือ iPhone ที่รัน iOS 17.4 และ 26/27 ใช้ `NSAllowsArbitraryLoads` + `handleChallenge` ต่อไปที่ LAN IP, public IP และ domain ทั้งแบบ HTTPS และ `wss://` รายการที่สองคือ Safari บน iPhone/iPad ต่อ `wss://` ไปยัง server self-signed ทั้งหลังกดยอมรับคำเตือนและหลังติดตั้ง CA เพราะหลักฐานที่มีตอนนี้เป็นรายงานปี 2020 ที่ WebSocket ไม่ผ่านแม้หน้าเว็บจะผ่านแล้ว ([galene #18](https://github.com/jech/galene/issues/18)) รายการที่สามคือ Android 17 ที่ targetSdk 37 ต่อ LAN และ NSD ทั้งตอนมี `ACCESS_LOCAL_NETWORK` ตอนไม่มี และตอนผ่าน picker รายการที่สี่คือ cookie `__Host-`/`Secure` บน origin self-signed ที่เป็น IP ใน Chrome, Firefox และ Safari รายการที่ห้าคือ Windows 10/11 ที่เปิด Defender สร้างและย้าย entry เป็นพันรอบขณะเปิดรูป slip ค้างไว้ รวมทั้งลอง root path ที่เป็นอักษรลาว คู่กับการทดสอบภาคสนามอีกหนึ่งรายการ คืออ่าน WAN ของ router ที่ร้านจริงแล้วทดสอบจาก 4G ตามขั้นในส่วนที่ 3 เพราะไม่มีข้อมูลสาธารณะใดบอกได้ว่าสายของร้านอยู่หลัง CGNAT หรือไม่

## บทสรุป

ปัญหาใหญ่ทุกข้อใน draft มีรากเดียวกัน คือ trust ถูกผูกไว้กับตำแหน่งในเครือข่ายผ่านสมมติฐานสามข้อ ได้แก่ "LAN = ปลอดภัย" "ครั้งแรกที่ต่อ = ของจริง" และ "IP เดียว = คนเดียว" สภาพจริงของลาวทำให้ทั้งสามข้อแตก CGNAT ทำให้หลายคนใช้ IP เดียวกัน relay ทำให้ internet ดูเหมือน loopback และ Wi-Fi สาขาทำให้การต่อครั้งแรกถูกดักได้ เมื่อย้าย trust ไปอยู่ใน artifact ที่ตรวจด้วย crypto คือ QR ที่พก pin คู่กับ device credential ตำแหน่งในเครือข่ายก็เหลือหน้าที่แค่ด้าน UX เช่นกำหนดว่า web client เป็น LAN-only หรือเลือก endpoint ที่เร็วที่สุด แล้วสามเรื่องที่ดูแยกกันก็ใช้กลไกเดียวกันหมด iOS ปิด ATS ได้โดยไม่เสียความปลอดภัยเพราะ pin มาจาก QR relay เป็นท่อโง่ ๆ ได้เพราะ TLS วิ่ง end-to-end และ password ลดเหลือ 8 ตัวได้เพราะไม่เคยเป็นสิ่งเดียวที่สร้าง session บนเครื่องใหม่

ผลข้างเคียงคือต้นทุนจริงของ "ฟรี" และ "ไม่พึ่งใคร" ชัดขึ้น iOS แบบฟรีไม่ได้ฟรีจริง แต่แลกมาด้วยคอมพิวเตอร์ที่เปิดตลอดทุกสาขา Apple ID ของร้านเครื่องละตัว และการงดอัปเดต iOS ต่อเนื่อง ส่วน "ไม่พึ่ง server ของคนอื่น" จะ lock ได้โดยไม่ขัดกับความจริงก็ต่อเมื่อนิยามใหม่เป็น "ไม่มี source of truth, key หรือ account อยู่นอกโฟลเดอร์ jar" เพราะ Telegram, provisioning ของ Apple และ VPS สำหรับร้านที่อยู่หลัง CGNAT ล้วนมีอยู่ใน plan แล้วหรือเลี่ยงไม่ได้ ลำดับงานที่ตามมาจึงเป็นการแก้ MASTER สี่ส่วน คือ Principles, Network, Login และ Stack/config ก่อน จากนั้นทำ device test ห้าข้อกับการเช็ก CGNAT ของสายร้านจริงใน P00 แล้วจึงปลด ⏳ ของ P06/P07/P11
